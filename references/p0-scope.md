# Phase 0 — 项目定位与范围确认（交互式）

本阶段是**交互式**的：必须与用户确认后才能进入 Phase 1。
产出（定位结论 + 审计范围 + 架构原则）写入审计文档头部的「定位与范围」节，后续所有判断以此为准。

## Step 0.1 整体梳理 + 定位建议

扫描仓库整体结构：子项目数量、技术栈、入口点、部署形态线索
（`*.sln`/`*.csproj`、`package.json`、`Dockerfile`、服务端框架、桌面框架、CLI 入口）。

**定位判定标准：**

| 定位 | 判定信号 |
|------|----------|
| **在线项目** | 存在对外网络服务（HTTP/API/Socket/WebSocket 服务端）、处理远程用户数据、部署到服务器/云、有鉴权体系 |
| **本地项目** | 桌面应用 / CLI / 本地后台服务，数据存本地，无对外服务端口，随操作系统运行 |
| **混合** | 两者并存（如「后端服务 + 桌面客户端」）——逐子项目分别标注定位 |

操作：
1. 输出定位结论 + 判定依据（引用具体文件/配置作为证据）
2. **让用户确认**。存疑时默认按「混合」处理并向用户说明。

## Step 0.2 排除目录清单

整理明显不需要审计的目录，给出清单 + 理由，**询问用户是否需要补充或删减**：

典型排除对象：
- 第三方库 / vendor / `node_modules/` / NuGet 还原目录
- 构建产物：`bin/`、`obj/`、`dist/`、`build/`、`target/`
- 生成代码：`*.g.cs`、`*.Designer.cs`、ORM 迁移产物、protocol 生成代码
- 测试基线数据、fixture 大文件
- 纯文档目录、图片资源、本地化资源
- 与本次审计目标无关的独立实验项目（需用户确认）

**输出格式**：目录 + 排除理由的表格，明确标注「以下目录将被排除，是否需要补充？」。

## Step 0.3 架构原则

**询问用户整体架构原则**，作为 Phase 2 中 D8 架构违规的判定基准：
- 分层规则与依赖方向（如「UI 不直接访问数据层」「基础库不反向依赖业务」）
- 模块边界与通信方式（事件/接口/直接调用）
- 命名与组织规范
- 明确的架构红线（如「禁止跨子项目直接引用内部类型」）

用户未给出时：列出业界通用分层原则（Presentation → Application → Domain → Infrastructure），
**明确说明将采用该默认基准并请用户确认**，不得静默假设。

## 产出（写入审计文档头部）

```markdown
## 定位与范围（Phase 0 结论）

| 项 | 内容 |
|----|------|
| **项目定位** | 在线 / 本地 / 混合（逐子项目标注） |
| **标注项过滤** | 定位=在线 → 查【在线】跳【本地】；定位=本地 → 查【本地】跳【在线】；混合逐子项目过滤 |
| **审计范围** | <目录/子项目清单> |
| **排除目录** | <目录 + 理由> |
| **架构原则** | <用户确认的原则，或"默认分层原则（已确认）"> |
```
