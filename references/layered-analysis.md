# Phase 1 — 分层架构分析（子项目定位 → 模块定位）

逐步深入：先定位子项目，再定位模块，最后在 Phase 2 逐文件深入。
本阶段产出 OVERVIEW.md 与 STRUCTURE.md 的初稿（Phase 3 定稿）。

## 1.1 子项目定位分析

对每个子项目（在 Phase 0 确认的范围内，排除目录除外）回答：

| 问题 | 说明 |
|------|------|
| **职责** | 一句话说明它做什么 |
| **架构角色** | 展示层 / 业务层 / 数据层 / 基础库 / 工具 / 服务端 / 客户端 |
| **依赖关系** | 依赖哪些子项目、被谁依赖（画出依赖方向，检测环） |
| **对外接口** | 提供什么（API / UI / CLI / DLL / 协议 / 队列） |
| **项目定位** | 在线 / 本地（决定该子项目审计时【在线】/【本地】标注项的取舍） |
| **风险初判** | 复杂度热点（大文件 Top）、可疑设计、与架构原则的潜在冲突 |

**同时标注**：不被任何子项目依赖也不提供入口的子项目（孤岛，转 G1 跟踪）。

## 1.2 模块定位分析

在每个子项目内部（按目录 / 命名空间 / 组件划分模块）：

| 问题 | 说明 |
|------|------|
| **职责** | 模块做什么，属于子项目的哪个关注点 |
| **对外暴露** | 其他模块允许使用哪些类型/函数，其余是否应收窄为内部 |
| **内部依赖** | 依赖哪些模块、被哪些模块依赖 |
| **与架构原则的关系** | 是否违反 Phase 0 原则（依赖方向、边界、红线） |

模块数量多时，按「核心 / 支撑 / 边缘」分级，Phase 2 深入时核心模块优先。

## 1.2b 数据库与多端清单采集（Phase 0 确认"有数据库 / 多端"时执行）

这两份清单是 Phase 2 中 D4 数据库三节与 D5 多端一致性节的**事实基础**，必须先建好：

### 表/列清单（数据库存在时）

- schema 真源优先级：迁移目录 > ORM 实体定义 > `schema.sql` > 代码内 `CREATE TABLE`
- 逐表列出：表名 | 列（名/类型/可空/约束/默认）| 主键 | 索引 | 外键 | 来源文件
- 标注每张表/每列的**代码引用位置**（`file:line`），标注是否"仅 DDL 声明"
- 产出 `SCHEMA.md`，供 D4 做双向差集（僵尸 vs 漂移）

### 端矩阵（多端时）

- 逐端列出：端名 | 技术栈 | 入口 | DTO/model 定义位置 | 承担的业务规则 | 与服务端的交互方式
- 列出关键业务规则清单（金额计算、权限判定、状态流转、校验规则、超时/重试、缓存策略）
- 产出 `ENDS.md`，每条规则留出"各端实现位置 + 是否一致"的对照列

**清单未建完，不要开始 D4/D5 的对应检查**——否则只能靠印象猜。

## 1.2c 用户可见文案清单采集（Phase 0 确认"有用户可见文本"时执行）

- 抽取全部用户可见文本：控件文本 / 菜单项 / 弹窗标题与正文 / 通知 / 状态栏 / 引导语 / CLI 提示 / 错误对话框
- 逐条记录：所在界面或触发点 | `file:line` | 当前文案 | 触发条件（何时出现）
- 标出**错误/异常路径**的文案（最常出现内部细节的地方）
- 产出 `COPY.md`，供 D6 逐条做"三问"判定

**注意**：AI 参与生成过的代码里，这类文案往往集中在"错误处理分支"和"新功能首次提示"两处，优先抽查。

## 1.3 文档模板（Phase 3 定稿到 `docs/audit/AUDIT-<YYYYMMDD>-<scope>/`）

### OVERVIEW.md — 项目综述文档

```markdown
# 项目综述 — <项目名>

## 定位与范围
（Phase 0 结论表：定位 / 类型维度 / 审计范围 / 排除目录 / 架构原则）

## 技术栈
（语言、框架、关键依赖及版本）

## 子项目清单
| 子项目 | 职责 | 架构角色 | 定位 | 依赖 | 风险初判 |
|--------|------|----------|------|------|----------|

## 架构图（文本）
（子项目依赖方向图；关键数据流 1-3 条按步骤列出）

## 关键结论
（架构层面的重要发现：环依赖、孤岛、红线风险）
```

### STRUCTURE.md — 结构文档

```markdown
# 项目结构 — <项目名>

## 目录树（标注审计范围）
（目录树，用注释标注：【审计】/【排除】+ 理由）

## 各子项目内部结构
（每个子项目：目录 → 模块划分 → 模块清单表）
| 模块 | 职责 | 对外暴露 | 依赖 | 级别（核心/支撑/边缘） |
```

### SUBPROJECT-<name>.md — 子项目分析文档

```markdown
# 子项目分析 — <name>

## 定位
职责、架构角色、依赖关系、对外接口、项目定位（在线/本地 → 决定标注项过滤）

## 模块分析
（每个模块一节：定位表 + 与架构原则的关系）

## 发现的问题
（本子项目范围内的 Phase 1 级发现：环依赖、孤岛、边界违规；文件级发现留待 Phase 2 汇入审计总文档）
```

模块分析内容多时可另出 `MODULE-<subproject>-<module>.md`，在子项目文档中留链接。

### SCHEMA.md — 表/列清单（仅"有数据库"时生成）

```markdown
# 数据库表/列清单 — <数据库名/类型>

schema 真源：<迁移目录 / 实体定义 / schema.sql>

## 表清单
| 表名 | 列（名/类型/可空/约束/默认）| 主键 | 索引/外键 | 代码引用位置 | 引用状态 |
|------|------------------------|------|-----------|-------------|----------|

## 双向差集结论（Phase 2 D4 回填）
- **僵尸表/字段**（schema 有、代码无）：<清单或"无">
- **代码引用不存在的表/字段**（代码有、schema 无）：<清单或"无">
- **仍写入但无人读取**：<清单或"无">
```

### ENDS.md — 端矩阵与业务规则对照（仅"多端"时生成）

```markdown
# 端矩阵 — <项目名>

## 端清单
| 端 | 技术栈 | 入口 | DTO/model 定义位置 | 承担的业务规则 | 与服务端交互 |
|----|--------|------|-------------------|----------------|--------------|

## 关键业务规则对照
| 规则 | 服务端实现 | Web | 桌面/移动 | CLI | 是否一致 | 差异说明 | 建议真源 |
|------|-----------|-----|------------|-----|----------|---------|---------|
```

### COPY.md — 用户可见文案清单（仅"有用户可见文本"时生成）

```markdown
# 用户可见文案清单 — <项目名>

## 清单
| 界面/触发点 | 位置(file:line) | 当前文案 | 触发条件 | 三问判定 | 问题类型 | 建议文案 |
|-------------|-----------------|----------|----------|----------|----------|----------|
```

> 三问：① 用户需要知道这句话吗？② 有没有只对开发者有意义的信息？③ 看完知道下一步做什么吗？
> 问题类型：A 暴露内部实现/判断逻辑 · B AI 口吻 · C 可操作性 · D 冗余风格
```

## Completion criterion

- 每个子项目有完整的定位表（无空白项）
- 子项目级依赖图无未定性的孤岛节点
- 每个模块有职责与级别标注，核心模块清单已确定（Phase 2 优先级依据）
- OVERVIEW.md 与 STRUCTURE.md 初稿已写出
